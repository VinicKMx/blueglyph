# USB Protocol Specification

Status: draft v1

This document defines the binary framing shared by nRF52840 firmware and the Python host.
Logs are not protocol messages.
Protocol frames are structured, versioned, and designed so the host can detect corruption and packet loss.

## Byte Order

All integer fields are little-endian.

## Frame Layout

```text
message_header
payload[payload_length]
crc32
```

Header layout:

```c
struct message_header {
    uint16_t magic;
    uint8_t protocol_version;
    uint8_t message_type;
    uint16_t payload_length;
    uint32_t sequence;
    uint64_t timestamp_us;
};
```

Constants:

```text
magic:             0xB1E0
protocol_version: 1
header_size:      18 bytes
crc32_size:       4 bytes
max_payload:      65535 bytes
```

`crc32` is computed over the encoded header bytes followed by the payload bytes.
It does not include the CRC trailer itself.

## Timestamp

`timestamp_us` is generated by firmware for hardware-originated events.
The host must not replace radio timestamps with USB arrival time.

Command responses and host-originated control messages may use `0` when no radio timestamp applies.

## Sequence

`sequence` is monotonic per firmware boot for transmitted frames.
The host uses gaps to detect loss or firmware reset behavior.

## Message Types

```text
0x01 RADIO_PACKET
0x02 DEVICE_STATUS
0x03 CAPTURE_STATUS
0x04 ERROR
0x05 COMMAND_RESPONSE
0x06 FIRMWARE_INFO
0x07 TIME_SYNC
0x08 STATISTICS
0x09 LOG
```

Unknown message types are allowed at the framing layer but may be rejected by higher protocol layers if unsupported.

## Host Commands

Host-to-firmware command payloads will be specified as typed payload schemas before they are used by transport code.
Expected command families:

```text
START_CAPTURE
STOP_CAPTURE
SET_CAPTURE_MODE
SET_CHANNELS
FOLLOW_CONNECTION
SET_FILTER
GET_STATUS
GET_VERSION
RESET
```

## Error Handling

The host parser must detect and report:

- invalid magic;
- unsupported protocol version;
- payload length above configured limit;
- truncated frame;
- CRC mismatch;
- sequence gaps;
- disconnects and firmware resets.

When the parser sees leading garbage bytes, it may resynchronize at the next valid magic sequence.
When a complete frame fails CRC validation, the frame is rejected and the session records a malformed frame.

## Compatibility

The protocol version changes when frame-level semantics are not backward compatible.
Payload schemas should prefer explicit lengths, reserved fields, and additive extension points when possible.
